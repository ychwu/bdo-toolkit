BDO Toolkit

BDO Toolkit passively reads live or recorded Black Desert traffic and returns structured Python objects for item events, inventory and storage state, and Arena of Solare rankings.

v0.1.0 · alphaPython ≥ 3.10passive · read-only

First use: choose whether the integration needs continuing item activity, the inventory and town-storage state sent during login or a character switch, or an Arena of Solare leaderboard result. Complete Capture setup before moving from replay to live traffic.

Shared transport, separate workflows

Every public workflow begins with the same transport vocabulary: captured packets are reassembled into a TCP stream and framed into BDO messages. After framing, only the selected workflow runs. Shared transport does not create one universal event or result type.

Item profiles are domain-specific. Item-event and item-state decoding use a selected item opcode profile; calibration rebuilds that profile after supported layouts move. Solare establishes identity from structural relationships and does not load an item profile.

Rules shared by every workflow

Passive and read-only

Live capture observes inbound server traffic, and replay reads saved packets. Neither path sends, injects, modifies, delays, or retransmits game traffic.

Capture-derived, not on demand

An event or snapshot states what the selected evidence supports at capture time. The toolkit does not request current account state from the game server.

Missing evidence remains missing

Depending on the owning API, absent or contradictory evidence becomes None, unknown, a skipped decode, or a non-complete result. It is not invented or silently treated as zero.

Public models outlive wire layouts

Observed opcodes and layouts can change after a game patch. Public models are the supported boundary, but the API is alpha; pin the package version and follow each domain’s patch guidance.

Captured data can be sensitive. PCAPs and serialized results can contain network endpoints, inventory or storage contents, leaderboard names, and performance statistics. Raw captures can also contain identifier-like opaque bytes that the toolkit does not decode or publish. Apply the integration’s retention and sharing policy; see Capture privacy.

Start with recorded traffic Recommended

A fixed recording is deterministic, requires no live-capture driver or adapter selection, and exercises the same domain decoding logic and public result model as the corresponding live workflow.

Replay paths: replay_pcap() for item events · analyze_item_state_pcap() for character-load state · replay_solare() for Solare. Before live capture: install the package and complete the platform prerequisites.

PacketCaptureOptions

Immutable network configuration shared by item-state capture, calibration, and Arena of Solare live capture.

PacketCaptureOptions(interface=None, local_ip=None, ports=(8884, 8885, 8889), use_bpf=True, auto_local_ip=True)

The object is optional. Each accepting API constructs PacketCaptureOptions() when capture_options=None. Supply one only to override documented defaults. Continuing item-event APIs instead accept the LiveCaptureOptions subclass.

Fields, defaults & validation

ParameterTypeDefaultContract
interfacestr | NoneNoneAdapter name passed to Scapy. None attempts default-route interface discovery. The name is not validated until capture starts, so Scapy or the operating system can reject it then.
local_ipstr | NoneNoneDestination IPv4 restriction. A supplied value must be valid IPv4 text and is normalized when stored; invalid text raises ValueError. With an explicit interface, None means no destination-IP restriction.
portstuple[int, ...](8884, 8885, 8889)Server source ports treated as BDO traffic. The collection must contain at least one non-boolean integer from 1 through 65,535. Invalid values raise ValueError; duplicates are removed while preserving first-seen order.
use_bpfboolTrueMust be an actual bool. True filters in the capture driver. False captures more traffic into the process and performs the same port/IP checks in Python.

Construction versus startup. Value validation happens when the object is created. Adapter availability, capture permissions, driver/BPF support, and default-route discovery are environment checks performed when capture starts.

Accepted by

Pass the object through capture_options= to CharacterLoadSession, calibrate_live(), CalibrationSession, AsyncCalibrationSession, capture_solare_snapshot(), or either Solare live session. Offline replay reads packets from a file and accepts its own ports parameter.

Select an adapter explicitly when automatic discovery is unsuitable. Run from scapy.all import show_interfaces; show_interfaces(), then pass one of the displayed Scapy interface names. Names such as "Ethernet" are machine-specific.

Guide Item events

Item events

Decode live or recorded Black Desert traffic into immutable BDOEvent objects for filtering, serialization, storage, and testing.

Normal live delivery reports item activity—offers, inventory receipts, storage withdrawals, and confirmed storage additions. Explicit snapshot filters can expose individual state records; assembled inventory and town-storage queries belong to the item-state API.

First use: complete Capture setup, then follow the Quickstart to print one decoded event.

From messages to events

The selected opcode profile is layout authority for the item decoder, not a value produced from the message. One recognized message can contain multiple records; each successfully decoded record becomes one immutable BDOEvent.

EventFilter controls delivery only. It runs after decoding and final classification, so filtering never changes which layouts the profile allows the decoder to understand.

Item decoding after patches

Profiles can go stale. There is no published protocol specification; game patches can change item opcodes or byte offsets and leave decoding quiet without an exception. Calibration rebuilds a local profile from known traffic.

BDOEvent exposes raw item IDs and does not include an item-name or marketplace catalog. See the event fields and stability contract.

Quickstart

Capture the first live item event as a BDOEvent with default delivery, or replay a saved recording when live capture is not needed.

Prerequisite: install the published package first. The Live tab also requires Capture setup; Replay requires an existing PCAP or PCAPNG recording.

1. Decode one event

from contextlib import closing

from bdo_toolkit import capture_live

with closing(capture_live(capture_seconds=30)) as events:
    for event in events:
        print(event.format_human())
        break
from contextlib import closing

from bdo_toolkit import replay_pcap

with closing(replay_pcap("path/to/session.pcapng")) as events:
    for event in events:
        print(event.format_human())
        break

Live: this quickstart listens for up to 30 seconds, so a no-event run ends instead of waiting indefinitely. While it is running, gather an item, collect a mob drop, or withdraw an item from town storage. Live capture uses the ordinary activity preset by default. Because the loop stops after its first event, closing() immediately closes the generator and stops the underlying capture session. Replay: replace the path with a PCAP or PCAPNG recording. Replay is exhaustive by default, but this shortcut reads only through the first delivered event; closing() releases the reader when the loop exits early. Both inputs yield the same BDOEvent model.

The live first-event shortcut does not drain the shutdown tail. Closing finalizes capture but cannot yield events finalized during that close, and the convenience iterator does not expose final capture health. Use LiveCaptureSession when the application must drain the complete tail, inspect health, or coordinate shutdown.

capture_live()

capture_live(*, opcode_profile=None, live_options=None, event_filter=None, capture_seconds=None, origin_observer=None, on_diagnostic=None) -> Iterator[BDOEvent]

The smallest live-capture API: a blocking iterator for scripts and command-line tools. With event_filter=None, it delivers the activity preset rather than character-load snapshot records.

Windows requires Npcap. Install Npcap and run with capture permissions before starting live capture. Offline replay requires neither.

Example

from bdo_toolkit import EventFilter, capture_live

potato_receipts = EventFilter(
    event_types={"item_received"},
    sources={"Gathering"},
    item_ids={7003},
)

for event in capture_live(event_filter=potato_receipts):
    print(event.event_type, event.source, event.item_id, event.quantity)
from bdo_toolkit import capture_live

for event in capture_live():
    if (
        event.item_id == 7003
        and event.event_type == "item_received"
        and event.source == "Gathering"

        print(event.event_type, event.source, event.item_id, event.quantity)

Both versions apply the same item ID, event type, and source criteria. Source matching is exact and case-sensitive. Quantity is printed but not constrained, so its value varies with the captured event.

Omitting a live filter is not exhaustive. Pass EventFilter.all() explicitly when snapshot and neutral records are required.

LiveCaptureSession

Controlled live-capture lifecycle for the continuing item-event API. It yields BDOEvent records while allowing capture to start and stop independently of incoming events; omitted filters use the activity preset.

LiveCaptureSession(*, opcode_profile=None, live_options=None, event_filter=None, origin_observer=None, on_diagnostic=None)

Asyncio counterpart: AsyncLiveCaptureSession preserves the same decoder, filter, single-consumer, shutdown-drain, and retained-error contracts with awaitable lifecycle control.

Consuming the stream Recommended

Primary consumption path

Use events() for long-running applications, CLI tools, workers, and services that can dedicate one thread or other blocking execution context to event consumption. It is an efficient blocking iterator: the consumer blocks on the session queue while no events are available and resumes promptly when a BDOEvent arrives; it does not continuously poll.

session.start()

for event in session.events():
    process(event)

Here, session and process() are supplied by the integration. Call stop() from the control or UI thread. The iterator then drains queued and shutdown-finalized events before ending. This loop is the session's single event consumer; fan out UI rendering, persistence, logging, and other downstream work from process(event). The synchronous API does not reject overlapping consumers, so the application must enforce this ownership.

Shutdown-finalized storage events remain observable. stop() closes pending origin windows and performs any supported neutral-record promotion before events() ends. The iterator drains those events in the same single-consumer loop.

poll() is the caller-timed alternative. Use it for timer-driven UI loops, nonblocking checks, or timeout-aware control flow. Do not call it alongside an active events() consumer.

Application integration examples

from threading import Thread

from bdo_toolkit import EventFilter, LiveCaptureSession

mob_drops = EventFilter(sources={"Mob Drop"})
session = LiveCaptureSession(event_filter=mob_drops)
worker_errors = []


def consume_events():
    try:
        for event in session.events():
            print(event.event_type, event.source, event.item_id, event.quantity)
    except BaseException as exc:
        if not worker_errors:
            worker_errors.append(exc)


worker = Thread(target=consume_events, daemon=True)


def on_start():
    session.start()
    print("Capture started")
    worker.start()


def on_stop():
    session.stop()
    worker.join()
    if worker_errors:
        raise worker_errors[0]
    session.raise_if_failed()
    print("Capture stopped:", session.stop_reason)
from bdo_toolkit import EventFilter, LiveCaptureSession

mob_drops = EventFilter(sources={"Mob Drop"})
session = LiveCaptureSession(event_filter=mob_drops)

def on_start():
    session.start()
    print("Capture started")


def on_ui_timer():
    while (event := session.poll(timeout=0)) is not None:
        print(event.event_type, event.source, event.item_id, event.quantity)


def on_stop():
    session.stop()
    on_ui_timer()  # Display events finalized during shutdown.
    print("Capture stopped:", session.stop_reason)

The events() worker is the default when a blocking consumer fits the application. It retains the first consumer failure, stops on the control thread, joins the worker, and re-raises instead of silently losing the error. The poll() form is for UI frameworks that own scheduling; invoke on_ui_timer() periodically and once after stop(). Both versions filter only by source="Mob Drop".

Storage events

This guide explains how to tell existing town contents, confirmed live additions, and neutral storage records apart before filtering or counting activity.

Need merged town contents from one character load? Use the storage aggregate and query model. Event-level contracts: destination identity and names · manual and worker origins · storage metadata in event.extra.

State, activity, and neutral records

In game terms, a snapshot record says that an item was already in a town’s storage when the character loaded. A delta says that a quantity was added to that storage during the captured session. A neutral storage record means the wrapper decoded, but the toolkit cannot safely choose between state and activity.

Delivery and batch behavior

decode neutral record→origin evidence→hydration cohort→apply EventFilter
  • Forward lookahead: live and neutral candidates can be delivered after later non-storage events while the tracker examines ordered worker companions in the same TCP flow. Timestamps are not changed.
  • Closure: a decision closes on confirmed evidence, the next complete message whose opcode belongs to a storage profile family known to the tracker, an invalid next-message header, eight following complete messages, replay/session finalization, or when the 2.0-second stale threshold is serviced.
  • Declared-count decoding: the profile’s record_count_offset, calibrated one-record base, actual message length, and every declared item, quantity, and instance must validate before any record emits. There is no generation-specific compatibility path.
  • Neutral multi-record promotion: a complete unresolved group receives one promotion decision and emits in record order. Incomplete or inconsistent groups remain neutral.
  • Hydration cohort: inventory hydration anchors a 30-second same-flow epoch; an anchored burst needs at least eight distinct destinations. Without an inventory anchor, a burst needs at least 17 destinations and one wrapper declaring at least eight records. Bursts are separated by a 0.5-second gap or one-second maximum span.
  • Boundary proof: storage records and inventory hydration anchors must match an independent top-level generic frame. If a midstream attachment leaves that scanner falsely synchronized, inventory-only recovery requires two fully decoded wrappers to be exactly adjacent on the same TCP generation; lone or nonadjacent nested signatures are discarded. Storage does not use this exception.

The 2.0-second value is a stale threshold, not a strict wall-clock delivery promise. Live polling services it; replay can instead close the decision through later traffic, end-of-file finalization, or another earlier boundary.

State assembly and live capture flow

Storage-sweep chronology Advanced

Hydration can contain more than one pass over storage destinations. The assembler first orders recognized groups, keeps tightly timed same-destination chunks together, and closes a destination block when the destination, empty/nonempty state, or one-second chunk window changes. Once a closed destination appears again, that repeat starts a new inferred sweep.

ordered storage groups→destination blocks→repeat starts next sweep→latest sweep selected
  • items, occupied_stacks, and query helpers expose only destinations and observed identities from the latest inferred sweep.
  • raw_records, groups, missing-identity counts, and superseded counters preserve diagnostics from every retained sweep.
  • A destination absent from the latest sweep remains discoverable as a summary with current_state_observed=False, but its older items are not presented as current.
Sweeps are conservative chronology, not a decoded lifecycle marker. A repeated closed destination is strong evidence of a new pass, but an operator-stopped capture can end partway through the selected sweep. Review storage_locations_not_selected_from_latest_sweep and warnings before replacing a complete local storage index.

How profiles work Optional background

Each game message carries a numeric opcode that helps identify its layout. A profile tells the toolkit which opcodes it can decode and where to find values such as item ID and quantity inside those messages. These identifiers and byte positions can change after a game patch.

Understanding a profile entry

One entry identifies a message layout and describes how to read its item records. This abridged calibrated storage entry uses illustrative patch evidence; the offsets are profile data, not decoder constants:

{
  "event": "STORAGE_ITEM_DELTA",
  "opcode": "0x1C51",
  "length": 270,
  "item_id_offset": 44,
  "quantity_added_offset": 48,
  "destination_instance_offset": 79,
  "context_offset": 8,
  "record_count_offset": 5,
  "repeat_stride": 228
}
  • opcode is the 16-bit identifier carried by the message. It selects the candidate layout.
  • length is the normalized single-record base message length and decoder minimum for this layout.
  • An *_offset is a zero-based byte position measured from the start of the message. Item IDs and quantities occupy four bytes; instance identifiers occupy eight.
  • context_offset is the calibrated four-byte destination-key position; record_count_offset is the calibrated two-byte declared-count position.
  • For a usable STORAGE_ITEM_DELTA record layout, each present prefix field must end at or before item_id_offset: context_offset + 4 <= item_id_offset and record_count_offset + 2 <= item_id_offset. Each prefix field is validated independently against the first-item boundary.
  • repeat_stride is observed item-record spacing used as calibration evidence; storage runtime derives the actual message stride from declared count, actual length, and the one-record base.

For this example, item_id_offset=44 reads the first item ID, context_offset=8 reads the destination key, and record_count_offset=5 reads the declaration used to validate and split the complete wrapper. Constructing an invalid MessageSpec raises ValueError; loading the same invalid geometry from a saved profile raises ProfileError. Recalibration can move every absolute value shown here.

Storage wrappers derive batch stride. When the calibrated declared-count field and complete record structure validate, the decoder combines that count with the one-record base length to derive the stride for the individual message. It does not select a patch-generation layout or require saved repeat_stride to match. See the exact geometry contract.

Profile families and event types

Under specs, uppercase keys such as STORAGE_ITEM_DELTA group entries that serve the same decoder role. This guide calls each key a profile family. A profile family can contain more than one entry.

Same-opcode entries must remain unambiguous. Entries that pass profile loading can share an opcode, but runtime decoding emits only when exactly one candidate validates the complete message. Zero valid layouts or several simultaneously valid layouts fail closed; profile order never selects an ambiguous interpretation. Loot-preview profiles apply the stricter length-domain rule below before runtime.

Loot-preview profiles are patch-specific. For LOOT_PREVIEW, item_instance_offset is optional but decode-affecting; absent geometry yields event.item_instance=None. Decode-identical layouts collapse to one runtime layout. Distinct layouts sharing an opcode raise ProfileError when their accepted message-length domains overlap, because profile order and plausible payload values cannot safely identify a patch layout. Disjoint exact-length variants remain supported. Any non-no-op advanced update_profile(..., replace=False) merge performs this check before backup or write; recalibration with default replacement is the repair path.

Calibration guide

Calibration passively observes controlled in-game item actions—normally storage deposits and withdrawals—to create or refresh a local opcode profile for current traffic.

Use action="auto" for routine transfer-profile calibration. It calibrates both transfer directions during one short capture session and is the only transfer mode normal integrations need. Explicit directions are advanced protocol tools; action="loot-preview" is a separate optional workflow.
Live calibration has the same capture prerequisites as live decoding. Windows requires Npcap, and every platform requires permission to capture on the selected interface; elevation depends on the operating system or Npcap configuration. Offline PCAP calibration requires neither.

When to run it: recalibrate after a game patch or when a previously working profile stops producing expected events.

Calibrate and write a profile

The one-call path uses calibrate_and_update() to observe the transfers, return the analysis, and write the promoted profile families after both primary transfer directions are proven. Calibration is passive: the call listens while the user performs all three in-game actions; it never moves items or changes the watched quantity between actions.

Choose an unambiguous town for calibration. Velia or Heidel are the recommended, well-tested choices, but they are not a hard-coded whitelist; another registered town can work when its destination column is unambiguous. Do not use Muzgar, Velandir, Yukjo Street, Godu Village, or Bukpo as the only destination in the capture. If one of those towns is involved, include a controlled deposit to an unambiguous registered town in the same capture. This restriction applies only while learning the destination column; the resulting profile decodes, names, filters, and snapshots all five towns normally. See the advanced authority explanation and storage-location registry.

Execution details

Item
Use five matching unstackable items sharing one known raw item ID. Pass the per-record quantity once, normally 1; it remains fixed for the whole session. The 1, 4, and 5 action counts are not quantity arguments; calibration derives record cardinality from the captured wrappers.
Capture window
Start calibrate_and_update() before the transfers. While it passively listens, deposit one matching unstackable, deposit the remaining four, then withdraw all five. Counts 1 and 4 let calibration intersect the one destination column and one declared-count column; the five-record withdrawal proves the reverse-transfer profile family and its repeated geometry. Avoid unrelated inventory or storage actions until capture ends.
Finish and verify
Press Ctrl+C immediately after the five-item withdrawal. Automatic transfer writing requires INVENTORY_TRANSFER and STORAGE_ITEM_DELTA; an incomplete nonempty result is refused before profile access. After a successful return, compare events_found with the integration’s runtime requirement subset. Discovering all five transfer profile families only means optional evidence was also recorded.

Serialized shape: deposit 1 → 1 record × quantity 1; deposit 4 → 4 records × quantity 1; withdraw 5 → 5 records × quantity 1.

Two distinct validated record counts are the minimum storage authority. Use one single plus one multi, or two different multi counts. The recommended counts are 1 and 4. These shapes prove context_offset and record_count_offset without a patch layout table, normalize the wrapper to one-record base length, and cross-check stride. For an unstackable batch, pass the quantity in each repeated record (normally 1), not the number of records. Stackable items are not rejected by item ID, but a stackable batch serializes as one record regardless of stack quantity and therefore cannot supply this two-count proof by itself.

If a required runtime profile family is missing

Do not use “all five transfer profile families found” as the runtime-readiness test. There is no single ok flag, and a result can omit optional calibration evidence while still containing every runtime profile family the integration needs. Compare events_found with that requirement set before repeating capture.

  • Confirm that item_id is the shared raw item ID and quantity is the value encoded in each matching record—normally 1 and fixed for the full recommended session—not the wrapper’s record count.
  • Start capture before the one-item deposit and finish after the five-item withdrawal.
  • Repeat the three-action sequence—deposit 1, deposit 4, withdraw all 5—without unrelated inventory or storage actions during capture.
  • Read result.summary() and result.events_found first; inspect result.ignored and direction evidence when a required runtime profile family remains missing.
  • A result missing only SOURCE_CONTAINER_DECREMENT or SOURCE_ITEM_REFERENCE does not require another run for current replay or live-capture behavior. Retry only when full calibration evidence is needed for review or troubleshooting.
  • If SOURCE_STACK_DECREMENT remains missing, calibration could not prove one unique usable decrement companion. Repeat the controlled sequence rather than copying offsets or a stride from another patch; the advanced geometry contract explains the fail-closed checks.
  • If CalibrationAuthorityError names destination-field and the capture used Muzgar, Velandir, Yukjo Street, Godu Village, or Bukpo as its only destination, discard that run and repeat the complete deposit-1, deposit-4, withdraw-5 workflow in Velia or Heidel. Changing towns resolves only destination-column authority; keep the distinct record counts and return transfer.
  • If CalibrationAuthorityError names record-count-field, capture at least two independently validated inventory-to-storage record counts—one single plus one multi, or two different multi counts—and retry. A town change does not replace this evidence.
  • If analysis returns a nonempty result but the later automatic write lacks either primary profile family, update_profile() raises CalibrationAuthorityError before profile access. The two-step caller can inspect that result; calibrate_and_update() raises before returning its tuple. Capture the missing direction or, after review, use the corresponding explicit action whose consistency the two-step caller owns.
  • If a newly written profile still reports storage_decoder_incompatible, retain a diagnostic PCAP: a deeper invariant may have changed.
Calibration discovers rotating positions, not every possible protocol redesign. It learns opcode, first-item position, one-record base, destination context_offset, and record_count_offset. Storage-wrapper candidate parsing still validates the shared storage-item record relationships (item+4 and item+35); source-decrement geometry is discovered separately. If those storage-record invariants or the count encoding itself change, safe calibration stops instead of producing a superficially current profile.

When storage authority is ambiguous Advanced

CalibrationAuthorityError means the target storage wrapper was present, but cross-frame evidence could not uniquely prove the destination and/or count column. The exception names destination-field, record-count-field, or both. Destination authority requires an unambiguous registered-town column; count authority requires at least two distinct validated record counts. No CalibrationResult is returned and the one-call update path writes nothing. This is different from a capture that never contained the target action.

Establish the destination column with registered-town evidence. Use Velia, Heidel, or another structurally compatible unambiguous town. Muzgar (0x055F), Velandir (0x0566), Yukjo Street (0x058C), Godu Village (0x0590), and Bukpo (0x05A4) each expose registered Velia (0x0005) one byte later in the observed wrapper; repeating different items or counts in only one listed town preserves both candidates. After one unique column is established, a structurally valid wrapper with no competing registered-ID candidate elsewhere in its prefix can confirm a nonzero unregistered destination at that column. An unknown-town-only capture cannot establish the column safely, but runtime preserves a later authoritative unregistered ID as UNKNOWN_STORAGE(0x…). No per-town calibration is required: runtime reads only the saved offset and supports all five listed towns normally. Changing towns does not replace the distinct-count or return-transfer evidence.
Calibration returns analysis objects, not gameplay events. Calibration APIs return CalibrationResult and related calibration types. Replay and live capture use the saved profile to yield BDOEvent objects afterward.

Alternative workflows: use calibrate_pcap() for repeatable offline analysis, the two-step calibration and update_profile() path to review before writing, CalibrationSession for independently controlled synchronous lifecycle, or AsyncCalibrationSession inside an existing asyncio application. Source-decrement geometry Advanced

When the decoded storage instance appears exactly once in a multi-record source-decrement candidate, calibration anchors it and discovers the quantity phase and record period without assuming their order or separation. Quantity and instance must fit without overlap in every field-valid repeated position. When the corresponding storage message exposes independently derived multi-record cardinality, the repeated candidate must match it exactly. Only one longest field-valid shape is retained; stride aliases and equal-longest ambiguous phases are withheld. Single-record or unanchored candidates remain governed by the structural or quantity-only fallback.

Learned geometry belongs to the selected profile. length, repeat_stride, quantity_removed_offset, and source_instance_offset are discovered evidence, not opcode- or patch-specific decoder constants. Runtime length and modulus checks remain strict. An ambiguous repeated shape is not promoted; other independently proven profile families can still appear in the result.

Storage-wrapper batches Optional background

A storage wrapper declares a positive two-byte little-endian record count N at MessageSpec.record_count_offset. MessageSpec.length supplies the calibrated one-record base B, and the message header supplies actual length L. Runtime accepts the declared geometry only after validating every record.

require N >= 1

if N == 1:
    require L == B
else:
    require L > B
    require (L - B) % (N - 1) == 0
    stride = (L - B) // (N - 1)
    prefix = B - stride
    require prefix >= 5
    require L - prefix == N * stride

The count field must fit inside the prefix. Calibrated item, quantity, and instance fields must fit wholly inside one inferred record, and every declared record must contain a plausible positive item ID, positive quantity, and nonzero/non-sentinel instance before any event emits. Structurally valid markerless records are retained. The message length may use the full unsigned 16-bit wire range through 65,535 bytes.

Geometry does not assign operation semantics. A valid wrapper emits neutral storage records. Independent origin evidence can prove live activity; a bounded multi-destination cohort can prove hydration. No mode byte, operation token, or July/August layout branch participates. Missing or contradictory count/destination authority fails closed and is surfaced through DecoderHealth.

Primary consumption path

Use async for when an asyncio application can dedicate one task to event consumption. The task waits efficiently while no event is available and resumes when a BDOEvent arrives; it does not block the event loop or continuously poll.

async with AsyncLiveCaptureSession() as session:

Arena of Solare

Classify live or recorded traffic from an in-game Arena of Solare Leaderboard refresh and receive one terminal SolareCaptureResult; confirmed rankings begin at result.snapshot only when result.complete is true.

First use: follow the offline replay. Need leaderboard or player data: open the common queries. Use the entry-point table when live or asyncio control is needed.

From capture to data

A complete in-game Leaderboard refresh contains two independent responses: the authoritative overall top 100 and 31 class-specific top-20 lists. Solare capture validates those responses together and returns one terminal result; it does not emit BDOEvent objects. A complete result exposes exactly one immutable snapshot, while every non-complete result keeps diagnostics and exposes no partial leaderboard.

Optional details finalize after structural proof. A registered geometry uses its reviewed decoder; an unregistered geometry runs bounded, ephemeral inference over the complete 620 + 100 records. Neither path can create a snapshot from incomplete structure, and Solare does not use item-event calibration or a user-managed opcode profile.

The async facade emits the same structured update kinds illustrated in the synchronous transcript above; only consumption uses async for/await.

One progress consumer and one completion waiter. One poll()/updates() consumer and one wait() caller may coexist. A second concurrent consumer or second concurrent waiter raises RuntimeError; a timeout-only wait leaves the session usable.

Cancellation requests and awaits bounded synchronous cleanup before it escapes. If cleanup cannot be verified within that bound, cancellation remains the caller-visible outcome, cleanup_incomplete stays True, and the same async facade and private executor remain available for an explicit cleanup retry.

A cancelled poll cannot consume a terminal update invisibly. If the synchronous poll completes while its async caller is being cancelled, any non-None update it removed is transferred to facade-owned pending storage. The next poll() or updates() call returns that update first. While capture is active, timeout validation still runs before pending progress. After completed stop, the argument is ignored while progress drains without waiting.

The async facade retains its private executor while cleanup is incomplete. Catch the failure or cancellation, inspect cleanup_incomplete, and retry await session.stop() on the same facade. The executor closes only after terminal cleanup is verified; there is no background cleanup retry.

  • poll(), wait(), and stop() require a started session.
  • The capture callback only enqueues packets. For each queued packet, the worker writes the original packet to the optional PCAP before performing reassembly and structural discovery; strict detail decoding runs during final result construction. After a decoder failure, remaining accepted packets are still recorded but are not fed into questionable semantic state.
  • on_update runs synchronously: capture-ready is emitted during start(), and later updates run in the Solare worker. Keep the callback lightweight or enqueue work. Call request_stop() for callback-driven shutdown. Blocking stop() and progress consumption are always prohibited there; synchronous wait() is also prohibited until a terminal result exists. Inside a terminal callback, read update.result or session.result directly.
  • An on_update exception becomes the session error and requests shutdown.
  • The public update queue keeps at most 64 newest updates. It is a coalescible progress channel, not a durable event log; the terminal finished update is newest and retained.
  • save_pcap is opt-in and refuses overwrite. Protect saved captures as sensitive data. With keep-listening and no caller deadline, the file can grow without a toolkit disk bound even though decoder memory stays bounded.

Windows buffer requirement: the Solare session requires configuration of its requested Npcap buffer to succeed; the default request is 64 MiB.

Final worker cleanup is bounded. The session allows up to 15 seconds for queued capture work, structural refresh, and optional detail finalization before reporting cleanup as incomplete. Retain the same session object and retry stop() when cleanup_incomplete is true.

Guide Arena of Solare Advanced

Structural discovery

Solare classification derives identity from relationships among complete ranked tables, not from an opcode supplied by a caller or profile. This page uses rich for the 31 class top-20 response, matching public evidence names such as rich_layout.

Confirmation pipeline

  1. The stream scanner synchronizes on chains of plausible generic BDO message headers and can attach in the middle of an existing TCP stream.
  2. Large zero-flag messages are grouped by TCP four-tuple, connection generation, observed opcode, and length. Reopening the same four-tuple creates a new generation, so independent TCP lifetimes cannot be combined. Opcode is only an opaque equality label.
  3. Discovery finds two record-like name fields, an increasing rank field, and their repeated stride without a seeded offset. Rich ranks must begin with exact 1 through 20, then remain positive, unique, and strictly increasing; gaps are valid after 20.
  4. A rich candidate must contain the complete set of 31 currently supported primary-class codes, each contributing exactly 20 unique name/rank records: 620 players total.
  5. A separate 100-player overall family must expose exact ranks 1 through 100, share at least 20 exact rank/name pairs with the rich table, and have no conflict in either direction: a shared rank keeps its name, and a shared name keeps its rank.
Why 20 is the safe minimum. The rich response is a union of class leaderboards capped at 20 entries. No player among global ranks 1 through 20 can have 20 same-class players ahead, so those first 20 must occur in the rich union under the supported table model. Rank 21 and later can be overall-only when a class exceeds the cap. This proof permits real gaps without accepting a weak unrelated-family join.
Opcode partitions candidates; structure establishes identity. Discovery reads the observed opcode as an opaque equality key so unrelated repeated message layouts remain separate. It never compares that key with a known Solare value or treats a match as confirmation. A patch may change opcodes, message lengths, strides, and identity offsets while the structural relationship still confirms.

Repeated refreshes and stale prefixes Optional background

A capture can begin midway through one refresh and then contain a complete retry, or contain one complete response followed by part of another. Discovery deduplicates retransmitted frames by flow generation, TCP stream sequence, message length, and message digest. It locates response boundaries from the invariant ten-frame rank prefix 1/2 through 19/20, then evaluates exact rich/overall windows only within those reset-aligned generations. Partial + complete + partial therefore recovers the middle refresh without accepting a mixed window.

When multiple complete snapshots are present, the one that first becomes complete in captured observation order wins. This order is assigned before family grouping and never compares unrelated TCP sequence origins across flows. Live capture permanently latches that exact frame window and its health; later traffic cannot erase or replace it. Replay feeds the same incremental tracker and classifier, so it has the same selection behavior.

Progress scans run at bounded absolute and reset-relative milestones, with one end-of-burst refresh for a completed retry whose final counts fall between those milestones.

Exact 50-frame ambiguity Optional background

Both ranked families carry two rows per frame, so the first 50 frames of another rich class table also expose ranks 1 through 100. Discovery explicitly rejects an exact 50-frame candidate when repeated class codes prove it is that class-table prefix. During an active live burst, a trailing 50-frame family also remains tentative: a following frame from the same family must reset to ranks 1/2 to close the prior generation, while ranks 101/102 prove it was a continuing rich table. Traffic from an unrelated family does not close it.

End-of-burst is evidence, not an opcode shortcut. If a valid overall response ends at exactly 50 frames, live capture confirms it on an idle/finalization end-of-burst refresh rather than necessarily at frame 50. Offline replay already has finalized input. If live traffic never supplies a same-family boundary and never becomes idle, confirmation waits until finalization.

Live tracking closes a valid trailing candidate only after the decode queue drains and 1.5 seconds pass without another leaderboard-sized candidate frame. Unrelated smaller game messages do not reset that candidate clock. A sustained decode backlog can delay clock service until already-delivered evidence is processed.

Capture integrity

The live leaderboard response can deliver more than five MiB in under a second. On Windows the Solare session defaults to a 64 MiB Npcap buffer and requires configuration of the requested positive size to succeed; lowering the value can reduce capture reliability. On every platform it keeps the packet callback minimal, moves writing and decode work to a worker, drains queued packets during shutdown, and reports available native drops plus TCP gap resets.

The Solare route uses per-flow reorder-pressure thresholds of 2,048 pending segments and 8 MiB of pending payload; the generic/item route retains its 128-segment default. These thresholds are separate from the 4,096-packet worker queue and the 768-frame / 16 MiB discovery window, and 8 MiB is not a global process-memory cap. If an anchored flow exceeds either threshold or its unresolved gap reaches 1.5 seconds, reassembly can reset at retained data. Any pre-confirmation reset makes health unclean, and live capture emits one immediate warning after the first reset.

Pre-confirmation discovery is bounded to 768 candidate frames and 16 MiB, and evaluates before evicting older candidates. A relationship whose required rich and overall halves are separated beyond that horizon is intentionally not assembled; rollover is reported so the operator can retry promptly. Live capture additionally bounds the packet handoff queue at 4,096, the polled progress queue at 64, and active TCP reassembly at 64 flows. Packet-queue overflow or flow-state eviction makes health unclean and prevents publication of a not-yet-confirmed snapshot; candidate-history rollover is reported separately because each retained window was evaluated before eviction.

Preserve a post-patch PCAP. Use save_pcap= or bdo-toolkit solare live --save-pcap ..., confirm zero reported drops/gaps, and replay the saved file. A second independent complete capture is stronger regression evidence than reprocessing one recording repeatedly.

Guide Failure semantics

Errors & reliability

An operation failure and an incomplete observation are different outcomes. Item capture stops fail-closed after known raw-packet queue loss; Solare returns a non-complete result when a clean, complete Leaderboard refresh was not proven.

The 250 ms grace is owner-serviced. It is not a background timer inside TCP reassembly. Item-event live sessions service it. Recovery probing is signature-directed. The item decoder groups configured layouts by their three-byte wire signature once when a scanner is constructed. Live capture produces no events

An empty event stream is not itself an error. The capture can be healthy while the selected interface, network constraints, profile, or event filter excludes all decodable traffic.

  1. Use an explicit session and inspect session.endpoint after startup, then its final session.health after stop. Resolve an unexpected adapter/filter or any unclean counter before interpreting silence.
  2. Confirm that the resolved interface carries the BDO connection and that the process has capture permission. Verify destination IP, server ports, and BPF settings; set use_bpf=False only when the local backend cannot install the filter.
  3. Pass EventFilter.all() temporarily to distinguish capture or decode failures from the live activity default or another delivery filter.
  4. If exhaustive delivery yields inventory_record, packet acquisition and inventory-record geometry worked, but the selected INVENTORY_TRANSFER layout lacks context authority. Recalibrate before treating the record as activity or character-load state.
  5. Confirm that the selected profile exists, is active, matches the current patch, and contains specs for the required profile families.
  6. Replay a short recording through replay_pcap() to separate deterministic profile/decoder behavior from live adapter setup.

Storage-specific diagnosis

  1. Pass EventFilter.all() and inspect event_type, storage_operation, storage_id, opcode, message_length, and record fields.
  2. If storage_record appears, the wrapper decoded but neither origin evidence nor hydration-cohort evidence claimed it. For an expected live deposit, check the calibrated decrement profile family and confirmed companion evidence. For expected existing state, confirm capture began before initial login or a character switch and continued until the playable world settled. An origin-promoted record would already appear as storage_delta; a hydration-promoted record would appear as storage_snapshot.
  3. If a known-live message appears as storage_delta with deposit_origin="unknown", decoding and operation classification succeeded; only cause evidence was missing.
  4. If no storage event appears with exhaustive delivery, inspect session.decoder_health and any on_diagnostic notifications. Verify the calibrated count and destination authorities plus item, quantity, instance, and length geometry. Decoder geometry or destination drift fails closed; it does not fall through to a patch-era mode/token layout or scan for a known-looking town key.

Configuration contracts: PacketCaptureOptions and LiveCaptureOptions. Startup failures: capture_live() errors.

Solare does not return a snapshot

A readable capture and a clean transport can still produce a non-complete result. Inspect status and evidence in this order:

  1. no-traffic: verify interface, local destination IPv4, server ports, permission, and BPF behavior.
  2. menu-context: only Solare menu or match-history-like traffic was recognized. During live capture, open or refresh the Leaderboard after capture-ready; if that action was already completed, preserve the capture and diagnose a missing or incompatible response.
  3. ranked-partial or rich-candidate: compare ranked_players, overall_players, and exact_cross_check. During live capture, leave the session running and refresh the Leaderboard again; discovery can isolate a complete retry after a stale prefix. Repeated clean failures after the complete action can indicate structural drift rather than only an early stop.
  4. detected-incomplete: inspect result.evidence.health.tcp_gap_resets, native drop counters, packet_queue_overflows, and flow_state_evictions. These diagnostics are conservative and capture-scoped. Fix acquisition and retry with a fresh capture; do not loosen classifier gates.
  5. inconclusive with clean health and a complete user action: check candidate_history_rolled_over, preserve the PCAP, and retry promptly or investigate structural-layout drift after a patch.
  6. complete with missing optional details: the rankings snapshot is still valid. Inspect both snapshot.class_table_capabilities and snapshot.overall_capabilities, then inspect result.evidence.rich_layout.detail_layout_id and result.evidence.overall_layout.detail_layout_id when those layouts exist. Missing totals remain unavailable and are never replaced by zero, the primary slot, a slot sum, or a class-table row. For a new geometry or repeatable registered-geometry detail failure, save and replay the PCAP; item calibration does not apply to Solare.

Status meanings: SolareDetectionStatus. Counts and integrity: Evidence and health. Patch boundary: structural discovery behavior.

Design principles

  • Passive by construction: no sending, injection, modification, delay, or gameplay automation.
  • Domain results stay distinct: continuing item capture returns BDOEvent; character-load state returns ItemStateSnapshot; Solare capture returns progress plus one leaderboard snapshot. Shared transport does not force a universal event shape.
  • Decode only selected routes: shared acquisition and reassembly run once, then only registered domain decoders receive messages.
  • Decode broadly, filter at the edge: item event filters control delivery, not decoder understanding. Live None uses the activity preset; explicit filters retain exact semantics.
  • Evidence over guesses: missing or contradictory structure becomes an unknown verdict, a neutral record, unknown item-state completion, a fail-closed skip, a non-complete Solare result, or an explicit error according to the owning contract.
  • State is not activity: existing inventory and town-storage records observed during initial login or a character switch are not new loot, transfers, or deposits. They feed a finite ItemStateSnapshot instead of the default live-activity stream.
  • Explicit writes: calibration analysis and origin learning do not mutate profiles automatically; item-state and Solare raw recording are opt-in and refuse PCAP overwrite.
  • Patch-aware ownership: item opcodes and ordinary record offsets live in replaceable profiles. Hydration adds structurally discovered and decoder-owned wrapper relations. Solare uses observed opcodes only as opaque family-partition and diagnostic labels; structural relationships establish identity, while deeper-layout invariants remain decoder-owned safeguards.

Capture, Solare, and origin-evidence privacy

Raw shared tokens are not persisted. Candidate files keep short BLAKE2 digests and opaque observation IDs for aggregation and replay deduplication.

That guarantee is limited to origin-candidate persistence. PCAPs, JSONL logs, serialized item events, and Solare results can contain timestamps, network endpoints, storage and inventory contents, and independently decoded names, rankings, Elo, overall aggregate outcomes, recent-result text, and per-class performance statistics. Raw captures may also contain identifier-like opaque bytes that the toolkit does not decode or publish. Protect, retain, and share those files according to the integration's data policy.

Solare does not retain opaque gear/loadout and skill-addon regions from either response by default. Python callers must opt in during acquisition with retain_raw_extensions=True and again during serialization with include_raw=True; CLI --include-raw deliberately performs both and writes the large unidentified ranges from players and overall_top_100 as hex. Do not enable or publish that surface merely because it is available; inspect and minimize the data required by the integration.
