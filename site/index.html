API Reference

BDO Toolkit

Passive, read-only packet telemetry for Black Desert Online. Feed it a capture — live or recorded — and get structured gameplay item events your app can consume.

live capture / .pcapng ──▶ reassemble · decode ──▶ BDOEvent stream
passive · read-only · never sends or modifies traffic

The toolkit observes server-to-client traffic only. It contains no code path that injects, modifies, delays, or replays packets to game servers, and no gameplay automation. Decoding is driven by a data file (the opcode profile) that you can recalibrate yourself when a game patch shifts the protocol.

Install

pip install bdo-toolkit

Or from a checkout: pip install -e ".[dev]" and run pytest.

Quick start

Replay a recorded capture and print every decoded event:

from bdo_toolkit import replay_pcap

for event in replay_pcap("session.pcapng"):
    print(event.format_human())

Filter to what your app cares about — here, worker deposits into storage:

for event in replay_pcap(
    "session.pcapng",
    event_types={"storage_delta"},
    sources={"Worker Deposit"},
):
    print(event.item_id, event.quantity)

Listen live (requires Npcap + admin on Windows) and stream events as they happen:

from bdo_toolkit import capture_live

for event in capture_live(event_types={"item_received"}, sources={"Mob Drop"}):
    print(event.to_dict())

Concepts

Events

Every decoded item record becomes a BDOEvent — a frozen dataclass with normalized fields (item_id, quantity, source, …) plus an extra mapping for provisional fields. The schema is additive: new optional fields may appear, existing ones don't break.

Opcode profiles

The wire protocol is observed, not documented — opcodes and byte offsets can shift with any game patch. Decoding is therefore driven by a JSON profile. A known-good default ships inside the package; when it goes stale, you calibrate a local one and pass it via opcode_profile=.

Filtering at the edge

The engine decodes every known category in one pass; the event_types / sources / item_ids arguments control only what is yielded to your app. Filtering never changes what the engine understands.

Replay a .pcap/.pcapng file and yield structured events in capture order. Works fully offline; no capture driver needed.

Path to a local opcodes.json. Default: the profile bundled with the package.

BDO server source ports to treat as game traffic. Default: (8884, 8885, 8889).

bdo_toolkit.capture_live()

capture_live(*, opcode_profile=None, interface=None, local_ip=None, ports=(8884, 8885, 8889), include_legacy_opcodes=False, ignore_opcode_profile=False, event_types=None, sources=None, item_ids=None, capture_seconds=None, no_bpf=False, no_local_ip_filter=False) → Iterator[BDOEvent]

Capture interface name. Default: auto-detected from the default route.
local_ipstr | None
Require this IPv4 address as the packet destination. Default: auto-detected unless no_local_ip_filter=True.
capture_secondsfloat | None
Stop automatically after this long. Default: run until the consumer stops iterating.
no_bpfbool
Disable the kernel capture filter and filter in Python instead — a fallback for adapters with broken BPF support.
(shared) 
opcode_profile, ports, include_legacy_opcodes, ignore_opcode_profile, and the three filters behave exactly as in replay_pcap().

bdo_toolkit.EventFilter

EventFilter.from_values(*, event_types=None, sources=None, item_ids=None) → EventFilter filter.allows(event) → bool

The same filtering used by the event_types/sources/item_ids arguments, as a standalone object — build one when your app filters events itself (for example, fan one decoded stream out to multiple consumers). A criterion left as None matches everything; set criteria must all match.

Writers

ConsoleEventWriter(stream=None) # default: sys.stdout JsonlEventWriter(stream=None) writer.write(event)

ConsoleEventWriter prints event.format_human() per event; JsonlEventWriter prints one sorted-key JSON object per line — pipe it anywhere. Both accept any text stream (a file handle, a socket wrapper, an in-memory buffer).

Opcode profiles

Opcode profiles

A profile is a JSON file mapping event categories to opcodes and byte offsets. The package bundles the maintainers' last calibration, so everything works out of the box.

Goes stale Opcodes and offsets can change whenever the game is patched. If events stop decoding after a patch, the bundled profile is stale — recalibrate a local profile and pass it via opcode_profile=. Never edit the file inside the installed package; keep local profiles in your app's config directory.

Calibration

How calibration works

You perform a known action in game — the classic: buy Potatoes (item 7003), move an exact quantity between inventory and storage — while the toolkit captures. It then searches every frame for that item id, scores candidate record layouts, and promotes the plausible ones into opcode specs.

Auto (the default) detects transfer direction from packet structure, so you don't declare which action is which — you move the item to storage and back (either order) and the toolkit classifies each leg itself. Direction is decided from the packet's own structure (validated across two opcode generations): a high-entropy source-context label before the record means the item is entering inventory (a receipt); a storage-delta reason code in the record means it is entering storage (a storage delta, which also covers worker deposits and multi-record unstackable moves). A nearby item-id reference frame is a fallback signal for older captures. Each candidate's classification is reported in result.evidence.

actionYou performDiscovers
auto (default)Move the item to storage and backBoth transfer families, direction auto-classified
storage-to-inventoryWithdraw the item from storageINVENTORY_TRANSFER, SOURCE_CONTAINER_DECREMENT
inventory-to-storageDeposit the item into storageSTORAGE_ITEM_DELTA, SOURCE_STACK_DECREMENT, SOURCE_ITEM_REFERENCE
loot-previewOpen a loot/gathering preview (optional, separate)LOOT_PREVIEW

Explicit single-direction actions are strict: if the capture's structure contradicts the declared action (in either direction — a declared deposit that looks like a withdrawal, or a declared withdrawal that looks like a deposit), calibration raises DirectionMismatchError and writes nothing, rather than promoting specs under the wrong event names. Auto never raises — it keeps whatever it can confirm. If neither structural feature can classify a capture at all, an explicit action still calibrates (a declaration with no contradiction stands — the post-patch recovery path), while auto drops what it cannot confirm.

Calibration is fully built in at three levels: a session object for apps, one-call wrappers for scripts, and the bdo-toolkit calibrate command for terminals.

calibration.CalibrationSession

CalibrationSession(*, item_id, quantity=None, action="auto", ports=(8884, 8885, 8889), interface=None, local_ip=None, context_frames=5, min_confidence=0.80)

Live calibration with programmatic start/stop — the API to embed in an app with its own UI. Capture runs on a background thread between start() and stop(); your interface stays responsive, and your app decides when the user is done:

from bdo_toolkit.calibration import CalibrationSession, update_profile

session = CalibrationSession(item_id=7003, quantity=3)  # action="auto"
session.start()
# your UI: "Move 3 potatoes to storage and back, then click Done"
# session.frames_collected → live counter for a traffic indicator
result = session.stop()          # user clicked Done
if result.specs:
    update_profile(result, "my_app/opcodes.json", replace=True)
start()→ None
Begin passive background capture; returns immediately. Raises RuntimeError if already running.
stop()→ CalibrationResult
End capture, drain pending TCP segments, score frames, return the result. Raises RuntimeError if the session was never started — a usage bug fails loudly instead of returning an empty result that looks like "nothing found".
runningbool (property)
Whether a capture is currently active.
frames_collectedint (property)
Frames decoded so far — drive a "traffic detected" indicator with it.
min_confidencefloat
Candidates scoring below this are rejected (with reasons, in result.ignored). Default: 0.80.
context_framesint
How many frames before a hit are searched for companion records (source decrements, references). Default: 5.

Also a context manager: with CalibrationSession(...) as session: stops the capture on exit even if the block raises. Call stop() inside the block to get the result.

calibration.calibrate_pcap()

calibrate_pcap(path, *, item_id, quantity=None, action="auto", ports=(8884, 8885, 8889), context_frames=5, min_confidence=0.80) → CalibrationResult

Calibrate offline from a pre-recorded capture of the known action. Same parameters as the session, plus the capture path. Fully deterministic — ideal for testing your recalibration flow.

calibration.calibrate_live()

calibrate_live(*, item_id, capture_seconds=None, quantity=None, action="auto", ports=(8884, 8885, 8889), interface=None, local_ip=None, context_frames=5, min_confidence=0.80) → CalibrationResult

Blocking convenience wrapper around CalibrationSession for console scripts. With capture_seconds it stops on a timer; without, it listens until Ctrl+C — which is treated as "action performed, calibrate now", not as an abort. Apps with their own UI should use CalibrationSession instead.

calibration.update_profile() / reset_profile()

update_profile(result, path, *, action="auto", replace=False, backup=True) → ProfileUpdate reset_profile(path, calibration_item_id=7003, *, backup=True) → Path | None

update_profile merges promoted specs into a local profile file (creating it if needed) and marks it active. Duplicate specs are skipped via structural dedupe keys, so re-applying a result is a no-op. With replace=True, the profile entries belonging to action are cleared first, so a recalibration fully supersedes stale entries. The previous file is backed up to opcodes_backups/ beside it unless backup=False.

reset_profile writes an empty active profile — a clean slate before a full recalibration.

Result types

CalibrationResult

FieldTypeMeaning
specstuple[OpcodeSpec, ...]Promoted opcode specs. Empty tuple = nothing plausible found.
ignoredtuple[str, ...]Rejected candidates with reasons (low-confidence, quantity-only, …) — show these when calibration fails.
frames_scannedintTotal frames analyzed.
evidencetuple[DirectionEvidence, ...]Per-candidate direction classification — which family each record was assigned and which structural features fired.

DirectionEvidence

Why a candidate was placed in (or excluded from) a transfer family: action, opcode, detected_family ("into_inventory", "into_storage", or None when neither feature fires), and the two feature booleans reference_frame, context_label, and storage_context. Use it to audit or display why auto calibration classified a capture the way it did.

OpcodeSpec

One discovered spec: event, opcode, length, the byte offsets that were located (item_id_offset, quantity_offset, item_instance_offset, context_offset, repeat_stride, …), plus confidence, score, and observed_at. to_json_dict() renders the profile-file form.

ProfileUpdate

What a write actually did: path, added (specs newly merged), replaced_events (categories cleared by replace=True), and backup_path.

Command line

bdo-toolkit CLI

Installed with the package. Every flag maps one-to-one onto a library keyword argument — the CLI is a convenience for terminals, not a separate capability.

# decode a capture as JSONL, filtered to worker deposits
bdo-toolkit replay session.pcapng --jsonl --source "Worker Deposit"

# live decode until Ctrl+C
bdo-toolkit live --event-type storage_delta --jsonl

# calibrate live (auto): move the item to storage and back, then Ctrl+C
bdo-toolkit calibrate --item-id 7003 --qty 3 --write opcodes.json --replace

# calibrate offline from a recording (dry run without --write)
bdo-toolkit calibrate --pcap move_both_ways.pcapng --item-id 7003 --qty 3

# start over with an empty active profile
bdo-toolkit reset-profile opcodes.json
CommandPurposeKey flags
replay <pcap>Decode a capture file--jsonl --profile --event-type --source --item-id --ports --include-legacy-opcodes --ignore-profile
liveDecode live trafficreplay flags + --iface --capture-seconds
calibrateDiscover opcode specs--item-id (required) --qty --action --pcap --capture-seconds --iface --min-confidence --write --replace --verbose
reset-profile <path>Write an empty active profile--calibration-item-id

Events go to stdout; status lines go to stderr — safe to pipe --jsonl output directly into other tools.

Stability & safety

  • Public surface: everything importable from bdo_toolkit and bdo_toolkit.calibration. Modules prefixed with _ are internal and may change without notice.
  • Additive schema: new optional BDOEvent fields may appear in any release; existing fields keep their meaning. Provisional fields live in extra first.
  • Passive by construction: the toolkit opens capture handles read-only and contains no packet-sending code path. It never automates gameplay.
  • Provisional knowledge: all offsets and labels come from observed captures. Treat confidence="observed" as exactly that.
